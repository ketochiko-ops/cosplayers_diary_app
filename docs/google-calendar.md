# Googleカレンダー連携

## 利用者の操作

連携は任意です。Googleに接続しなくても、指定JSONファイルまたはブラウザ内への保存は継続します。今回の連携対象はWeb/PWA版です。iPhone/iPadのSafariを含む複数端末で、同じGoogleアカウントの専用カレンダーを使用できます。ネイティブアプリのGoogle認証は未実装です。

1. 最初にアプリのプロジェクト保存方法を指定します。
2. 設定の「Googleカレンダーに接続」を押します。送信対象を確認し、「接続して同期」で自分のGoogleアカウントを選んで許可します。
3. アプリは「コスプレ日記」という専用の副カレンダーを作成、または以前のものを再利用します。個人の通常カレンダーへ予定を書き込みません。
4. 初回接続時に日記を同期します。接続後は、その日の最初に保存した日記の変更だけを自動同期します。以後は「今すぐ同期」を使います。自動同期はOFFにもできます。
5. 自動・手動・接続時・競合解決の同期は、端末/ブラウザごとに合計1日10回までです。通信失敗も1試行として数えます。再読み込み・アカウント切替では回数をリセットしません。端末の日付が変わると更新します。別端末、別ブラウザ、ブラウザデータ削除後との共通管理は行いません。
6. 上限到達、認証失効、オフライン、競合の場合も、編集とJSON/ブラウザへの保存は継続します。未同期の変更を表示し、必要に応じて翌日または手動で同期します。接続ボタンによるGoogle認証、カレンダーの検索/作成、表示切替は日記同期の10回とは別です。10回はGoogle APIのリクエスト数ではなく、同期操作の上限です。

Googleのトークンはメモリ内だけに置くため、アプリの再起動後は再接続が必要です。アプリを閉じている間の同期や定期ポーリングは行いません。

## 表示・非表示

新規専用カレンダーは最初は非表示です。設定の「Googleカレンダーに表示」で切り替えられます。Googleカレンダー側でも、一覧の「コスプレ日記」のチェックを外せば非表示になります。カレンダーを削除する必要はありません。非表示でも予定の保存と本アプリの同期は行えます。連携解除でもGoogle上のカレンダー・予定は削除しません。

## Geminiで見つけやすい予定

予定名の例: `[コスプレ] 作品A / キャラクターA / 制服`

説明には「活動日・活動種別・作品・キャラクター・衣装・メモ」を日本語で記載します。任意の予定名を日記フォームで設定でき、GoogleやGeminiが変更した予定名・活動日も取り込めます。予定は終日・予定あり/なしは「予定なし」・通知なし・非公開です。

Gemini側で同じGoogleアカウントを使用し、連携アプリのGoogle Workspaceを接続します。設定画面から次の質問例をコピーできます。

> @Google Calendar 「コスプレ日記」カレンダーから、今月のコスプレ活動を作品・キャラクター別に教えて

[Google公式のGeminiカレンダー連携説明](https://support.google.com/gemini/answer/15305236?hl=ja)は副カレンダーの利用に対応しています。Geminiの利用可否、表示を外したカレンダーの検索挙動、回答の精度はGoogle側の提供条件によります。本アプリからGemini APIを呼び出したり、自動的にGeminiへデータを送信したりはしません。回答は元の予定で確認してください。

## 同期範囲と競合

- 同期対象: 日記の活動日、活動種別、予定名、メモ、関連する作品/キャラクター/衣装の識別子と名称。別端末で不足する関連マスターは追加します。既存マスターは上書きしません。
- 対象外: 写真、写真ファイル、カラコン製品・購入・在庫・使用履歴、未使用のマスター、マスターの個人的なメモ。本アプリ全体のバックアップにはJSONを使用します。
- 専用カレンダーでGoogle/Geminiが作成した単発の予定は「その他」の日記として読み込みます。繰り返し予定は未対応で、勝手に展開せずエラーを表示します。
- 同期履歴を使い、片側だけの変更は反映し、両側の変更は競合として端末側/Google側を選びます。削除は以前に同期した日記だけに伝播します。新しい端末の空データからGoogle上の日記を消しません。
- Googleの変更日時だけで勝者を決めず、ETagで他端末の更新を検査します。書き込み結果不明時も自動リトライをせず、次回同期で確認します。
- 日記IDに対応する予定IDとGoogle側の非表示メタデータで重複を防ぎます。Googleの追加情報上限に合わせて分割し、大きすぎる情報は黙って切り捨てず停止します。
- カラコン使用履歴のある日記の日付をGoogle側で動かした場合は、使用履歴の不整合を防ぐため停止します。使用を解除してから同期します。同期で日記を削除するときは既存台帳の削除ルールで使用を解除します。
- 同期中に別の編集を検出した場合は、端末の変更を上書きせず、手動再同期を求めます。プロジェクトファイル/JSONを切り替えた際は連携を解除し、以前の同期履歴を使った一括削除を防ぎます。
- 1回の同期は外部更新100件まで。超える場合は残件を手動で続けます。Googleの一覧はページを取得し、20ページを超えた場合は途中の一覧を正本として使わず停止します。

## 運営者の設定

Google Cloudの管理権限を持つ運営者が設定します。利用者にクライアントIDの作成・入力は求めません。

1. [Google Cloud Console](https://console.cloud.google.com/)にアプリ用プロジェクトを作り、Google Calendar APIを有効化します。
2. Google Auth Platformでブランディング、問い合わせ先、対象ユーザー「外部」を設定します。テスト中はテストユーザーを登録します。
3. データアクセスに次の2スコープを追加します。
   - `https://www.googleapis.com/auth/calendar.app.created`: アプリ作成の副カレンダーとその予定を操作するため。
   - `https://www.googleapis.com/auth/calendar.calendarlist.readonly`: 専用カレンダーを他の端末からも検索・再利用するため。通常カレンダーの予定内容の読取権限は要求しません。
4. 「ウェブアプリケーション」のOAuthクライアントを作り、承認済みJavaScript生成元に `https://cosplayers-diary-app.vercel.app` を登録します。必要な開発元は `http://localhost:<実際のポート>` を追加します。生成元にパスは付けません。
5. GitHubのSettings → Secrets and variables → Actions → Variablesへ、Repository variable `GOOGLE_CALENDAR_CLIENT_ID` を登録します。値は `...apps.googleusercontent.com` 形式の公開クライアントIDです。クライアントシークレットは組み込みません。
6. `develop` ブランチの公開ワークフローを実行します。ビルドは `--dart-define=GOOGLE_CALENDAR_CLIENT_ID=...` を使用します。未設定時は連携ボタンを無効にし、アプリ内の保存機能は利用できます。
7. 一般公開前にホームページ、プライバシーポリシー、ドメイン所有確認を整えます。Google Auth Platformに表示されるスコープ分類・審査要件に従って検証し、OAuthを本番公開へ切り替えます。テストユーザー以外での接続と、Safari/Chrome/Edgeでの実接続を確認します。

GitHub Pagesの検証版は承認済みJavaScript生成元に `https://ketochiko-ops.github.io` を追加します（リポジトリのパスは不要）。Repository variable `GOOGLE_CALENDAR_PREVIEW_CLIENT_ID` があれば検証版だけでそのIDを使い、なければ `GOOGLE_CALENDAR_CLIENT_ID` を使います。本番の外部データを変更しないようテスト用Googleアカウントを使用します。配信手順は [`pwa-preview.md`](pwa-preview.md) を参照してください。

現在の実装には運営者のGoogle OAuthクライアントや認証情報は含めていません。実Googleアカウントへの書き込みとGeminiでの検索は、運営者設定後に検証が必要です。

## 利用量と費用

通常のGoogle Calendar API利用は標準枠内で無料ですが、標準枠超過の課金計画があります。[Google公式の料金・割当](https://developers.google.com/workspace/calendar/api/guides/quota)を公開前と利用増加時に確認してください。端末ごとの10回制限は呼び出し削減のためで、全利用者を合算したCloudプロジェクトの課金上限を保証する仕組みではありません。同期の失敗を自動で繰り返さず、差分のある日記だけを書き込みます。表示設定やOAuth処理は別の通信です。
